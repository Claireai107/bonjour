# 회원가입 DB · 인증번호 · 앱 버전 관리 구현 정리

> 기준 문서: `참가신청서_본주르_ver3.docx`
> 반영 버전: v1.0.0 (2026-08-06)

기획서에 적어 놓고 코드에는 없던 세 덩어리(회원가입 DB / 인증번호 / 앱 버전 관리)를
실제 동작하는 코드로 채운 내용입니다. 어떤 문장이 어떤 파일로 증명되는지 정리했습니다.

## 1. 기획서 문장 ↔ 구현 대응표

| 기획서 문장 | 구현 위치 | 상태 |
|---|---|---|
| 회원가입 시, 인증번호 제한 | `app/api/auth/send-code/route.ts`, `verify-code/route.ts` | 유효 3분 · 재발송 60초 쿨다운 · 24시간 5회 · 입력 5회 제한 |
| 암호화DB 테이블 관리 (최소한의 정보만 수집) | `supabase/schema.sql`, `lib/crypto.ts` | 이름·휴대폰·생년월일·성별·지역만 수집, 식별 컬럼은 암호문 |
| DB 물리적/논리적 분리 (users / health_records) | `supabase/schema.sql` | 테이블 분리 + UUID 참조, 건강 테이블에 식별정보 없음 |
| 최소 권한의 원칙 (분석 계정은 건강정보 읽기만) | `schema.sql` §7 `bonjour_analyst` | `health_records` SELECT만 부여, `users` 접근 REVOKE |
| 인증 5회 연속 실패 시 계정 접근 잠금 | `app/api/auth/login/route.ts` | 5회 실패 → 10분 잠금, 성공 시 카운트 초기화 |
| 감사 로그 및 접근 권한 관리 | `audit_logs` 테이블 + `lib/db.ts` `audit()` | 가입·로그인·인증 발송/실패/잠금 이력 적재, IP는 해시로만 |
| 생년월일, 로그인 연동 정보 → AES-256 컬럼 암호화 | `lib/crypto.ts` `encrypt/decrypt` | AES-256-GCM (인증 태그로 위변조 탐지까지) |
| 비밀번호 → Salt 적용 일방향 해시 | `lib/crypto.ts` `hashSecret/verifySecret` | scrypt + 16바이트 랜덤 Salt, 복호화 불가 |
| 전송 구간 TLS 1.2 이상 | Vercel 기본 (HTTPS 강제) | 인프라 제공 |
| 저장 데이터(Data-at-Rest) 암호화 | Supabase 기본 (디스크 암호화) + 컬럼 암호화 이중 적용 | 인프라 + 애플리케이션 |
| 암호화 키를 DB와 분리된 저장소에서 관리 | `APP_ENCRYPTION_KEY` / `APP_HASH_PEPPER` 환경변수 | 코드·DB 어디에도 키 없음 |
| 버전 태그(v1.0, v1.1…)를 부여하여 복구 지점 관리 | `lib/appVersion.ts` + git tag | 앱 버전이 코드 한 곳에서 관리됨 |
| 점검 안내 화면 | `app/maintenance/page.tsx` + `middleware.ts` | `MAINTENANCE_MODE=1` 로 전체 전환, 30초마다 복구 자동 확인 |

## 2. 인증번호 — 왜 이렇게 만들었나

**발송 채널과 인증 로직을 분리했습니다.**
실제 문자 발송은 건당 과금(알리고 8.4원, 네이버 SENS 9원)이라 시연 단계에서는 비용이 붙습니다.
대신 인증의 본질인 **제한 로직**은 전부 서버에 실제로 구현했습니다.

| 항목 | 값 | 근거 |
|---|---|---|
| 코드 유효시간 | 3분 | 탈취된 코드의 유효 창을 좁힘 |
| 재발송 쿨다운 | 60초 | 문자 폭탄·발송 비용 남용 차단 |
| 번호당 일일 한도 | 5회 | 같은 번호 반복 요청 차단 |
| 입력 시도 한도 | 5회 | 6자리 무차별 대입 방지 |
| 코드 저장 방식 | Salt 해시 | DB가 유출돼도 코드를 알 수 없음 |
| 성공 후 처리 | 즉시 소진 | 같은 코드 재사용 불가 |

`SMS_MODE` 환경변수로 발송 방식을 바꿉니다.

- `mock` (기본) — 실제 발송 없이 화면에 코드를 띄웁니다. **비용 0원**, 심사·시연용.
- `sms` — `send-code/route.ts` 의 `sendSms()` 안쪽만 실제 API 호출로 바꾸면 됩니다.
  이때 `mockCode` 는 응답에서 자동으로 빠집니다.

## 3. 회원가입 DB — 두 가지 모드

`SUPABASE_URL` 과 `SUPABASE_SERVICE_ROLE_KEY` 가 있으면 실제 Postgres,
없으면 서버 메모리로 동작합니다. 화면 코드는 어느 쪽인지 몰라도 됩니다.

**실제 DB로 붙이는 순서**

1. supabase.com 에서 무료 프로젝트 생성
2. SQL Editor 에 `supabase/schema.sql` 전체 붙여넣고 실행
3. Settings → API 에서 URL 과 `service_role` 키를 복사
4. Vercel → Settings → Environment Variables 에 아래 4개 등록 후 재배포

   ```
   SUPABASE_URL=https://xxxx.supabase.co
   SUPABASE_SERVICE_ROLE_KEY=...
   APP_ENCRYPTION_KEY=(아무 긴 문자열, 새로 생성)
   APP_HASH_PEPPER=(아무 긴 문자열, 새로 생성)
   ```

> `service_role` 키는 RLS를 우회하는 키입니다. 서버(API Route)에서만 쓰이며
> 클라이언트 번들에 포함되지 않습니다. 절대 `NEXT_PUBLIC_` 접두사를 붙이지 마세요.

**주의 — 무료 플랜은 7일간 요청이 없으면 프로젝트가 일시 정지됩니다.**
정지돼도 데이터는 남아 있고 대시보드에서 복구하면 되지만, 발표 직전에 깨어나느라
30초쯤 걸릴 수 있습니다. 심사·발표 기간에는 하루 한 번이라도 앱에 접속해 두거나,
Vercel Cron 이 하루 한 번 `/api/keep-alive` 를 호출하도록 `vercel.json` 에 넣어 뒀습니다.

## 4. 앱 버전 관리 · 롤백

버전 번호는 `lib/appVersion.ts` 한 곳에만 있습니다.

**배포할 때**

1. `APP_VERSION` 을 올린다 (기능 추가 `1.1.0` / 버그 수정 `1.0.1`)
2. `CHANGELOG` 맨 위에 한 줄 추가
3. 커밋 후 같은 번호로 태그

   ```bash
   git tag v1.1.0 && git push origin v1.1.0
   ```

**장애가 났을 때**

1. Vercel 환경변수에 `MAINTENANCE_MODE=1` → 재배포
   → 모든 화면이 '점검 중' 안내로 바뀝니다 (오류 화면 노출 방지)
2. 직전 정상 태그로 되돌린다

   ```bash
   git checkout v1.0.0
   ```

   또는 Vercel Deployments 목록에서 이전 배포의 **Promote to Production**
3. 원인 수정 후 `MAINTENANCE_MODE` 를 지우고 재배포

**사용자 쪽 버전 갱신**
PWA로 홈 화면에 추가하면 화면이 기기에 캐시됩니다. `components/UpdateBanner.tsx` 가
5분마다 `/api/version` 을 확인해 서버 버전이 더 높으면 업데이트 배너를 띄웁니다.
마이페이지 맨 아래에도 현재 버전이 표시돼, 문의가 들어왔을 때 어떤 배포본인지 바로 확인됩니다.

## 5. 아직 남은 것

- **오류 모니터링** — API 실패 자동 로깅·이메일 알림, 사용자 오류 제보 채널 (본선 해커톤 예정)
- **PIN·생체(FIDO) 재인증** — 리포트 열람 시 재인증. 스키마와 잠금 로직은 준비돼 있어
  화면만 붙이면 됨
- **회원 탈퇴 / 데이터 삭제 화면** — `on delete cascade` 로 DB는 준비됨

## 6. 기획서 쪽에서 한 줄만 고쳐 주세요

기획서 표에 비밀번호 해시가 **Bcrypt** 로 적혀 있는데, 코드는 Node 표준 라이브러리의
**scrypt** 로 구현했습니다. 둘 다 Salt 기반 일방향 해시이고 scrypt 는 메모리 하드 방식이라
GPU 무차별 대입에 더 강합니다. 외부 패키지 설치 없이 동작한다는 실무적 이점도 있습니다.

> 수정 문구 예시: `비밀번호, 간편 비밀번호` → **Salt를 적용한 일방향 해시(scrypt) 알고리즘 적용 (복호화 불가)**

## 7. 법적 요건 반영 (v1.1.0)

> 참고: 법률 자문이 아니며, 실서비스 전 전문가 확인이 필요합니다.

### 반영한 것

| 근거 | 내용 | 구현 |
|---|---|---|
| 개인정보보호법 제15조 | 개인정보 수집·이용 동의 | 필수 체크 + 전문 |
| **개인정보보호법 제23조** | **민감정보(건강정보)는 일반 개인정보와 별도 동의** | 별도 필수 체크 + 별도 전문 |
| **위치정보법 제19조** | **위치정보 이용 동의** | 선택 체크 + 전문, 미동의 시 GPS 호출 자체를 하지 않음 |
| 개인정보보호법 제30조 | 처리방침 공개 | `/privacy` 페이지, 마이페이지 메뉴에서 접근 |
| 안전성 확보조치 기준 | 접속기록 1년 보관 | `audit_logs`, 동의 항목까지 기록 |

동의 시각은 `users` 테이블에 항목별로 따로 남깁니다
(`consent_at` / `consent_sensitive_at` / `consent_location_at`).
동의 증빙이 필요할 때 어떤 항목에 언제 동의했는지 확인할 수 있습니다.

### 아직 남은 것 (실서비스 전)

- **개인정보 국외 이전** — Supabase 프로젝트 리전을 **Seoul(ap-northeast-2)** 로 만들면
  국외 이전에 해당하지 않습니다. 리전은 나중에 변경할 수 없으니 생성 시점에 골라야 합니다.
- **위치기반서비스사업 신고** — 방송통신위원회. 1인 창조기업·소상공인은 사업 개시 후
  1개월 유예. 공모전 단계는 해당 없으나 사업화 시 필요합니다.
- **의료기기 해당 여부** — 식약처에 질의(무료)해 회신을 받아두면 웰니스 제품 주장의
  근거 자료가 됩니다.
- **처리 위탁업체명 명시** — 처리방침의 위탁 표에 실제 업체명을 적어야 합니다.
- **회원 탈퇴 화면** — DB는 `on delete cascade` 로 준비돼 있고 화면만 없습니다.
